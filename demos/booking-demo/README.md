# Telegram Mini App для записи на приём: демонстрационный образец

Одностраничное мини-приложение для стоматологии. Клиент выбирает услугу, дату и время,
оставляет имя и телефон и видит подтверждение.

Это **демо**, а не готовый продукт:

- цены и услуги приведены как пример;
- расписание свободных слотов генерируется в браузере, реального расписания нет;
- заявка сохраняется только в `localStorage` браузера и **никуда не отправляется**:
  ни в клинику, ни в Telegram, ни на сервер;
- бот, базы данных, оплаты и админ-панели нет.

Файл: `index.html`. Вёрстка, стили и скрипт лежат в нём, внешний скрипт только один:
официальный `https://telegram.org/js/telegram-web-app.js`. Если он не загрузился,
страница работает как обычный сайт.

Что уже реализовано: мобильная вёрстка, тема Telegram (цвета, safe area, MainButton,
BackButton, haptics), выбор услуги, 14 дней, слоты времени, маска телефона, валидация,
экран подтверждения и локальный список заявок.

## Что нужно, чтобы это стало рабочим продуктом

### 1. Бот и токен

1. В Telegram открыть `@BotFather`, выполнить `/newbot`, получить токен вида
   `123456789:AAExampleTokenDoNotUse`.
2. Токен хранить **только на сервере**, в переменной окружения `BOT_TOKEN`.
   В HTML, JS и в git токена быть не должно: любой, кто открыл страницу, увидел бы его
   и получил полный контроль над ботом.
3. В BotFather: `Bot Settings` -> `Menu Button` -> указать HTTPS-адрес мини-приложения.
   Либо отправлять кнопку из бота:
   `{"inline_keyboard": [[{"text": "Записаться", "web_app": {"url": "https://example.ru"}}]]}`.
4. Домен обязан быть HTTPS с валидным сертификатом. GitHub Pages годится для демо,
   для клиента лучше свой домен.

### 2. Куда уходит заявка: webhook и backend

У мини-приложения нет доступа к токену бота, поэтому оно не может само отправить
сообщение. Схема из двух звеньев:

**А. Мини-приложение -> ваш backend.** В демо вместо этого `localStorage`. В рабочей
версии `submit()` делает:

```js
await fetch('https://api.example.ru/api/booking', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    initData: Telegram.WebApp.initData,
    serviceId: 'clean',
    date: '2026-10-21',
    time: '12:30',
    name: 'Иван',
    phone: '+79991234567',
    comment: ''
  })
});
```

**Б. Backend -> Telegram Bot API.** Сервер проверяет данные, сохраняет заявку в базу
и отправляет уведомление администратору через `sendMessage`.

Отдельно нужен webhook для самого бота, чтобы принимать команды, `callback_query`
от кнопок «Подтвердить» и «Отменить» и служебные события:

```bash
curl -X POST "https://api.telegram.org/bot$BOT_TOKEN/setWebhook" \
  -d "url=https://api.example.ru/tg/webhook" \
  -d "secret_token=$WEBHOOK_SECRET" \
  -d 'allowed_updates=["message","callback_query"]'
```

Это два разных адреса, их часто путают:

| Адрес | Кто вызывает | Зачем |
|---|---|---|
| `POST https://api.example.ru/api/booking` | мини-приложение | принять заявку из формы |
| `POST https://api.example.ru/tg/webhook` | серверы Telegram | команды бота и кнопки админа |

Обязательные требования к backend:

- **Проверка `initData`.** Подпись считается по алгоритму из документации Telegram:
  `secret = HMAC_SHA256("WebAppData", BOT_TOKEN)`, затем HMAC от строки
  `data_check_string` сравнивается с полем `hash`. Без проверки кто угодно отправит
  поддельную заявку с чужим именем.
- Валидация полей на сервере: длина имени, формат телефона, услуга из белого списка,
  дата и время из доступных слотов.
- Ограничение частоты: не больше 1 заявки в минуту с одного `tg_user_id` и IP.
- Проверка `secret_token` у webhook через заголовок `X-Telegram-Bot-Api-Secret-Token`.
- Ответ мини-приложению только после записи в базу.

Альтернатива без backend: `Telegram.WebApp.sendData(JSON.stringify(...))` и
`close()`. Данные приходят боту как `web_app_data`. Ограничения: работает только
для кнопок `web_app` в личном чате, полезная нагрузка до 4096 байт, нет подтверждения
доставки и нет защиты от повторов. Для формы записи с несколькими полями лучше backend.

### 3. Где администратор видит заявки

Нужно решить до запуска. Рабочие варианты:

1. **Сообщение в Telegram (минимум).** Бот присылает заявку в личный чат администратора
   или в общую группу клиники. В сообщении: услуга, дата, время, имя, телефон,
   номер заявки. Ниже кнопки «Подтвердить», «Перенести», «Отменить» на `callback_query`.
   Плюс: уведомление приходит сразу, ничего дополнительно открывать не надо.
2. **Панель заявок (рекомендуется).** Страница `/admin` за авторизацией: список заявок,
   фильтр по дате и статусу, поиск по телефону, статусы «новая», «подтверждена»,
   «отменена», «пациент пришёл». Авторизация через Telegram Login или отдельный пароль
   с двухфакторной защитой. Панель читает ту же базу, что и бот.
3. **Внешняя система.** Google Sheets, amoCRM, Bitrix24 или YCLIENTS через API.
   Имеет смысл, если клиника уже там работает и не хочет вторую панель.

Минимальная схема таблицы `bookings`:

```sql
CREATE TABLE bookings (
  id            BIGSERIAL PRIMARY KEY,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  service_id    TEXT NOT NULL,
  service_name  TEXT NOT NULL,
  price         INTEGER NOT NULL,
  slot_date     DATE NOT NULL,
  slot_time     TIME NOT NULL,
  client_name   TEXT NOT NULL,
  client_phone  TEXT NOT NULL,
  tg_user_id    BIGINT,
  tg_username   TEXT,
  status        TEXT NOT NULL DEFAULT 'new',
  comment       TEXT
);
CREATE UNIQUE INDEX bookings_slot_unique ON bookings (slot_date, slot_time)
  WHERE status <> 'cancelled';
```

Уникальный индекс не даст двум клиентам занять одно время. Ошибку нужно обрабатывать
и предлагать другое время, а не показывать 500.

### 4. Реальное расписание вместо заглушки

Сейчас слоты считаются функцией от даты: интервал 30 минут, воскресенье короче,
часть слотов помечена занятыми псевдослучайно. В рабочей версии:

- таблица рабочих часов по дням недели и исключениям (праздники, отпуск врача);
- длительность услуги влияет на сетку: чистка 60 минут занимает два получасовых слота;
- занятые слоты читаются из базы, а не из браузера;
- часовой пояс клиники фиксирован, пересчёт на клиенте не используется;
- при записи слот блокируется транзакцией, иначе две одновременные заявки пройдут
  проверку и создадут дубль.

### 5. Юридические требования

- Чекбокс согласия на обработку персональных данных и ссылка на политику
  конфиденциальности. В демо текст согласия декоративный.
- Персональные данные (имя, телефон) хранить на серверах в РФ, уведомление
  в Роскомнадзор об обработке ПДн. Состав и необходимость уточнять у юриста.
- Не хранить лишние поля, ограничить доступ сотрудников, настроить срок хранения
  и удаление по запросу.

### 7. Чего в демо нет

Нет бота, сервера, базы данных, авторизации, оплаты, уведомлений и реального
расписания. Нет проверки подписи `initData`. Нет защиты от спама. Заявки видны
только в том браузере, где их создали, и исчезнут при очистке данных сайта.
